# Architecture: the harness in the platform

How the harness code is shaped so that an agent can hold the whole of it, prove it works without a deployed Worker, and change one place to change one thing. Words are defined in [`CONTEXT.md`](../CONTEXT.md); what to build is in [`PRD.md`](PRD.md); the design and why is in [the spec](../prd/Harness%20v1%20-%20Architecture.md); why the shape is this way is in [`adr/`](adr/). The platform the harness sits in is designed in [the plan](../prd/An%20App%20For%20Everything%20-%20Platform%20Architecture%20Plan.md).

## The layout

```
apps/uw-app/            Hono on Cloudflare Workers: SSR pages and islands, command API,
                        MCP surface, live hub (Durable Object), Workflows, crons
apps/uw-app/ports/      platform adapters, one file per port (or port.variant), each beside its contract test
apps/uw-ingest/         webhook verification and enqueue; nothing else
packages/harness/       the kernel: pure TypeScript over ports; no Worker, vendor or
                        database import; the stage machine, ship rule, replay, walker
packages/contracts/     commands, events, outcomes and the verb registry as Zod; one
                        live version, golden fixtures, conformance test
packages/db/            Drizzle schema (the source of truth), migrations, constraints
packages/db/store/      the one Drizzle implementation of Store and Grants that both adapters bind
packages/core/          acl (can, principal), dates, modules registry, shared Zod schemas
packages/ui/            design tokens as CSS (tokens/), the Tailwind 4 theme over them (app.css)
                        and the built stylesheet committed as generated/app-css.ts (pnpm ui:css)
sim/                    test adapters for every port, fixture harnesses, scenarios, CLI
sim/adapters/           test adapters, one file per port, each beside its contract test
infra/                  wrangler configs, Access policies, environments; declared, never clicked
```

The listing is by role, not by import direction. Dependencies form this DAG, and dependency-cruiser and ESLint enforce exactly it:

```
packages/contracts  → nothing
packages/core       → contracts
packages/db         → contracts, core
packages/ui         → nothing
packages/harness    → contracts, core            (types only; no side effects)
apps/uw-app         → harness, db, contracts, core, ui      composition root
apps/uw-ingest      → contracts, core, db                   composition root
sim/                → harness, contracts, db                composition root
```

`apps/uw-app` and `sim/` are the composition roots that construct the kernel with adapters. `apps/uw-ingest` is a root too, but it never touches the kernel: it verifies webhooks and enqueues, and the queue consumer inside `uw-app` is what hands the event to the kernel. `packages/harness` is the pure layer: it may import `packages/contracts` and `packages/core` types and nothing with side effects. Everything durable is in Postgres through the Store port; nothing in the kernel knows it is Postgres. `sim/` imports `packages/db` because its Store adapter runs the real schema and migrations.

## The kernel over ports

```ts
createKernel(ports: Ports): Kernel

Kernel = {
  walk(stages): WalkPath[],
  templateProperty, replay,
  events, reads, items, repair, stages, delegations, gates, personas,
  health(),
}
```

The kernel has no `shipRule` member: the ship rule is called only by the Ship assembler (`packages/harness/gates/approve-at-ship.ts`, below), and `shipRule` stays exported from the `@uw/harness` index for its tests. Step 5 added `items.importIssue` and `items.labelRemoved` (the issue import and a removed label, import principals only), `reads.importTarget` (the harness a repository's issues import onto) and `reads.issueImported` (whether an issue already has an item), and `gates.recoverConnectors` (a person with `admin` recovers a lost connector result).

"Kernel" is the pure core. "Engine" means only the code behind the model-vendor seam (`claude-messages` and the rest).

One composition root per process. The Worker calls `createKernel` once with platform adapters. A test or the sim calls it many times with test adapters. Nothing else constructs a module. The kernel reaches everything outside itself through a port, the database included:

| Port | Provides | Platform adapter | Test adapter |
|---|---|---|---|
| Clock | now | `Date.now` | settable, advanceable |
| Ids | next id | `crypto.randomUUID` | sequential |
| Store | rows of every harness table, in transactions | Drizzle over Hyperdrive to Neon | the same Drizzle adapter over an embedded Postgres (PGlite) running the real migrations from `packages/db` |
| Grants | resolve a principal's grants; lock and re-read them | `role_grants` with `SELECT ... FOR SHARE` | the same queries on the embedded Postgres, with a scripted revoke |
| GitHubFacts | `pullRequest(ref)`: a PR's repository, head SHA, head ref and head repository, base SHA and ref, the repository's default branch, checks and reviews on the head, the changed files with the head and base they were compared at, and the parsed declaration; `refresh(ref)`: the same after re-reading GitHub | `apps/uw-app/ports/github-facts.ts`: `pullRequest` reads the `gh_*` read model only; `refresh` re-reads the PR, its reviews, its check runs and its files from GitHub through the one upsert path (`not_wired` with no GitHub client) | fixture facts per commit, `refresh` answered from the same fixtures |
| Connectors | `run(request)` for merge, deploy, publish, send, post; `outcomeOf(request)`, which reports an effect that already happened without causing one | `apps/uw-app/ports/connectors.ts`: `merge` is the squash-merge connector `apps/uw-app/github/merge.ts` with the ship GitHub client (`not_wired` without one); `deploy`, `publish`, `send` and `post` answer `not_wired` | records calls and answers scripted outcomes |
| ModelEngine | one persona turn: tool calls over the verb registry | the six engines, each in its own directory | scripted tool calls |
| Hub | wake a harness's clients | `apps/uw-app/ports/hub.ts`: posts the harness id to the `HarnessHub` Durable Object named by it, bounded at 2 seconds; the not-wired hub while `HARNESS_HUB` is unbound (until go-live) | records wakes |
| Notifier | `notify(wake)`: web push to the recipients' devices and one post to the item's Zulip topic, answering a decision per recipient and one for Zulip | `apps/uw-app/ports/notifier.ts` over `apps/uw-app/notify/`: web push through `@block65/webcrypto-web-push` (RFC 8291 `aes128gcm`, RFC 8292 VAPID) and Zulip's messages API, each bounded at 5 seconds; the not-wired notifier with no database | `sim/adapters/notifier.ts`: the same rank and cooldown choice, no devices and Zulip off until a scenario turns them on |
| Runs | start, resume, hibernate a run | Cloudflare Workflows | an in-process loop |

Every port has a platform adapter and a test adapter, and may have more than one platform adapter: ModelEngine has six. Validators are a registry inside the kernel, picked by key from a stage row; they are kernel code, not a port.

**One contract test per port.** Each port has one shared test suite that runs against every adapter of that port, so a test adapter and a platform adapter cannot drift. A port without a contract test fails a check.

**No hand-written database.** The Store test adapter is real Postgres semantics: the real schema, the real migrations, the real constraints and triggers. Nothing in the sim imitates a table.

**What only real Postgres can prove, and where each runs:**

| Guarantee | Embedded Postgres, in the sim and unit tests | Postgres service container in CI |
|---|---|---|
| The null-safe stage check: `('merge','checks')` and `('merge', NULL)` refused on insert and update | yes | yes |
| `harness_events` refuses UPDATE and DELETE; positions are assigned in order under a per-harness lock held to commit | yes | yes, with two connections for the position order; the `uw_app` role's missing UPDATE, DELETE and TRUNCATE grants |
| Claim is one conditional UPDATE: a second claim on a held item is refused | yes, sequentially | yes, with N concurrent connections |
| WIP limit: the count and the claim are one transaction | yes, sequentially | yes, with two claims racing one slot |
| The gate decision's locked grant re-read: revoke then decide, and decide then revoke | no; it needs two connections | yes |

PGlite is a single connection, so every test that races two connections runs against a Postgres server: the service container in CI, or any server `TEST_DATABASE_URL` points at locally. Neither needs an account or a secret; the Neon branch per pull request is go-live wiring (PRD FD-12).

## What is durable, and who writes it

Every durable value has one writer. The Drizzle schema declares every table with its classification (plan §2.6) and the kernel module that owns it. The schema is split by domain: `packages/db/schema.ts` holds the harness tables and re-exports `packages/db/schema-platform.ts`, which holds the platform tables (`people`, `role_grants`, `grant_audit`, `pages`, `page_versions`, `webhook_deliveries`, `queue_watermarks`, `tasks`, `service_tokens`). Everything imports `schema.ts`, and drizzle-kit reads it; a new table goes in the file for its domain.

| `harness_items` | the kernel | stage, holder, lease, risk tier and domains, expected head, and the issue an imported item wraps (repository, number, GitHub id; unique on the GitHub id) |

## Transactions and locks

A kernel command opens one transaction (`ports.store.transaction`) and passes the transaction object as-is to everything it calls; transactions never nest. A second transaction opens only after the first has settled: to record a refusal after Postgres aborted the first (`stage_edit_refused`), or to record a connector's outcome after the decision committed. The lease sweep lists lapsed leases in one transaction and expires each item in its own.

Locks are taken in one order, and none after the first event append:

1. **The breaker lock.** `harness-breaker` (one key for every harness, because the level is the latest breaker event on any harness) is taken before anything else by the two kinds of command that read the level to act on runs: the spend breaker takes it exclusive (`tx.lock`) to record a reading, and every resume of a hosted run (`resumeOne`, for a gate decision, a lane or harness resume and the breaker's `open`) takes it shared (`tx.lockShared`, `pg_advisory_xact_lock_shared`) and then reads the level. A resume that waits behind a reading sees that reading, so a run woken while the breaker records `pausing` stays hibernated for the breaker; resumes do not wait on each other (S7-R68).
2. **The stage lock.** The stage command and activation take `harness-stages:<harnessId>` before anything else and read the stage rows after it, so two edits of one harness serialise and neither writes back a row the other changed. Claim, take over and the gate decision take `harness-stage-claims:<stageId>` and re-read the stage after it, so the WIP count and the claim are one serial step; claim also re-reads the harness there, so an agent's claim that waited sees a pause committed meanwhile (S6-R50). Pause and resume take only `harness-stages:<harnessId>`. Reorder takes `harness-stage-claims:<stageId>` for the item's stage, then locks the stage's open items (those not done, read through `openInStage`) one row at a time in ascending id, and reads the open items again until no new one appears; it never locks a done item, and it appends after the last row lock (S6-R58). Enqueue and kickstart through the command API name no priority, and the kernel places the new item 1000 below the lowest open priority in the first stage (`harnessItems.read.lowestOpenPriority`), so fresh items never tie and a move between two of them writes one event. One command takes both, always in this order: a stage edit that changes a stage's connector takes `harness-stages:<harnessId>` and then `harness-stage-claims:<stageId>` for that stage, and only then reads the approvals at the stage that wait for a connector outcome (`decision_in_flight` if any does), over the stage's open items a page of 50 at a time, stopping at the first that waits. No command takes `harness-stage-claims:` before `harness-stages:`, so the two cannot deadlock, and a gate decision that waits behind the edit re-reads the stage and routes on the connector the edit left. The decision records the connector it routed through and the stage it routes to in the `gate_decisions` row's evidence (`connector`, `next`), and recovery runs that connector and advances to that stage, not the ones the stage rows hold later; it falls back to today's rows only for a decision recorded without `next`, or when that stage no longer exists.
3. **The item row.** `harnessItems.read.lock` locks the row by its id alone (`SELECT id FROM harness_items WHERE id = $1 FOR UPDATE`) and reads the item and its stage in a second statement after the lock (S5-R48), and `recordItemEvents` folds the locked row. A lock that joined the stage dropped the row when the command it waited on had moved the item to another stage (Postgres re-checks the joined condition after the wait), so the waiter answered `item_not_found`; every caller re-checks the item's stage and state after the lock instead.
4. **Grants.** `grants.lockAndReread` (`FOR SHARE` on the person's `role_grants`) where a revoke must wait for the command (the stage and gate commands); `grants.resolveIn`, a plain read in the same transaction, for the write-level checks of the item commands.
5. **The run row.** `harnessRuns.read.lock` (`SELECT ... FROM harness_runs ... FOR UPDATE`), or the run's `INSERT` or `UPDATE`, comes after the item row and the grants and before the appends (S7-R65). A run-host command that starts from a run id reads the run without a lock to find its item, locks the item, checks the delegation and the grants, and only then locks the run and re-checks its outcome. Start inserts the run after the claim; a step locks or inserts it after the holder and standing checks; submit notes the gate on the run after the gate's own writes; stop and prompt take the item, then the person's grants `FOR SHARE`, then the live run; hibernate, resume, complete, fail, halt and the held premise take the item and then the run. Nothing but the appends follows the run row. `recordItemEvents` locks the item row again before it appends, which takes no new lock because the command already holds it.
6. **Appends.** The `harness_events` insert trigger takes `harness_events:<harnessId>` and holds it to commit, so positions become visible in order. Taking any lock after it would hold the harness's append lock while waiting.

The issue import has no stage to lock either. `kernel.items.importIssue` and `kernel.items.labelRemoved` take `github-issue:<githubId>` first, then read the item by its issue (`harnessItems.read.byIssue`); `labelRemoved` then takes the item row, and both append last. Two imports of one issue, from a webhook and from the sweep, serialise there, so the second finds the first's item and the unique index on `harness_items.issue_github_id` is only the backstop. The issue page is written before, in its own transaction (`apps/uw-app/pages/issue-pages.ts`), and the cross-reference comment after.

The cross-reference claim is one conditional `UPDATE` of the `gh_issues` row, outside any kernel transaction (`apps/uw-app/github/facts/cross-reference.ts`): it sets `xref_claimed_at` only where no comment is recorded and no claim is younger than 10 minutes, and the caller posts only if a row came back. Recording the comment id and releasing the claim are single conditional updates on the same row, the release only for the claim's own instant. No lock is held while GitHub is called.

Connector recovery (`kernel.gates.recoverConnectors`) reads in one transaction (the harness, the person's `role_grants` `FOR SHARE`, the stages, every item's events), asks `Connectors.outcomeOf` for each stuck approval outside any transaction, and then records each item in its own transaction: the item row, the person's grants `FOR SHARE` again (an admin revoked meanwhile records nothing), the events read under the lock (an outcome recorded since is skipped), then the appends. It follows the order above.

Persona activation has no stage to lock, so it takes `persona-activation:<pageId>` first; a second activation of the same page waits there and then finds the item the first opened through the `persona_activation_failed` evidence (page and verb), so a missing verb opens one open item per persona page and verb however many attempts race and whatever the persona is renamed to. It then re-reads the activator's grants (`FOR SHARE`), reads what it needs, and takes `harness_events:<harnessId>` for the persona's harness and then for the software harness before the first append; its appends go in that order, the `persona_activation_failed` event first and the software item after it. When the tool check and the dry run pass, activation flips the page with one conditional `UPDATE ... WHERE status = 'suggested' AND version = $expected` (the page row lock, held to commit) and its `page_versions` snapshot, then upserts the `personas` row, then takes `harness_events:<harnessId>` and appends `persona_activated`. The dry run is pure and calls no port, so it adds no lock. A second activation of the same page waits on `persona-activation:<pageId>`, then finds the page `active` (`not_suggested`) or at a newer version (`stale_version`).

A page update (`apps/uw-app/pages/store.ts`) takes `pages-reparenting` first only when it moves the page to a parent other than the stored one (a plain read decides), then the page row (`SELECT ... FOR UPDATE`), in that order, and checks the stored version, parent and status under that row lock; a save that skipped the lock and finds the parent moved under the row lock is `stale_version`. No page transaction takes a kernel lock; the only kernel transaction that locks a page row is persona activation, after `persona-activation:<pageId>` and the grants and before the `personas` row and the appends.

A delegation lapse is an `UPDATE` of the delegations row (`delegations.write.markLapsed`, from `recordLapse` or `markLapse`) inside claim, submit, step, release, the beat, the scene and hibernation. It comes after the item row and the grants and before the run row, so it sits between steps 4 and 5 above. A run-host command that finds the delegation lapsed marks it first, then locks the run and stops it, then appends `delegation_lapsed` and the run's events. The minute cron's expiry sweep (`kernel.delegations.lapseExpired`) marks a lapse too: it reads the expired, unlapsed delegations outside any transaction, then takes one transaction per delegation that re-reads the row, marks it with the conditional `UPDATE` and appends `delegation_lapsed`. It takes no item, grant or run lock, so it is a sub-sequence of the order above.

The spend breaker (`kernel.breaker.check`) reads the spend outside any transaction, then records the reading on each harness in its own transaction, in ascending harness id: each takes `harness-breaker` exclusive first, re-reads that harness's latest breaker event under it, and appends only when the level differs or the last reading is five minutes old or more, so two overlapping checks record once. It then hibernates or resumes each run in its own transaction (item row, run row, append) through the same functions as pause and resume (S7-R56). Those functions re-check under the item and run locks what holds the run: a hibernation records nothing when the pause it was chosen for has been lifted, or the breaker is no longer `pausing`; a wake-up (by a lane resume, a gate decision or the breaker) re-tags the run as hibernated for the pause while the item's lane or harness is paused, so only the lane's resume wakes it, and while the breaker is `pausing` it re-tags the run as hibernated for the breaker, so only the breaker's `open` wakes it. The level is the newest breaker event by instant; at one instant the lowest harness id holds it, because every check records in ascending harness id.

The hosted beat's start takes `harness-run-persona:<persona>` before anything else and re-reads that persona's live runs on the harness under it, so two overlapping beats start at most one run per persona. No other command takes that key.

Linking an item's Zulip topic takes `zulip-topics:<harness>` after the item's row and before it reads the topics the harness's other items hold, so two items whose refs collide cannot link the same topic. No other command takes that key.

Binding a service token (`apps/uw-app/agents/service-tokens.ts`) takes `acl-grant-commands`, then the acting admin's `role_grants` `FOR SHARE`, then the bound person's `people` row (`lockPerson`, `FOR UPDATE`), then that person's `role_grants` `FOR SHARE`, in that order; revoking takes the first two and then updates the `service_tokens` row. Neither takes a kernel lock.

The GitHub read model (`apps/uw-app/github/facts/upsert.ts`) writes one batch of facts in one transaction and takes no kernel lock, and no kernel transaction locks a `gh_*` row. Before any write it locks, `FOR UPDATE ... ORDER BY github_id`, the batch's stored issues and then every pull request the batch touches: those it carries, and those named only by its reviews or its file lists. It then locks, in the same order, every `gh_repos` row holding an incoming repository id or an incoming name (case-insensitively), and gives a row whose name another repository in the batch now claims the placeholder `owner/moved.<githubId>`, so a renamed repository's old name can be taken over without breaking the unique name; the old row gets its real name from the next event that carries it. It then writes the tables in one order (repositories, milestones, issues, pull requests, check runs, reviews, files), with each table's rows sorted by GitHub id, so `INSERT ... ON CONFLICT` locks them in id order too. A batch therefore never holds a repository row while it waits for a pull request row, and two batches naming the same rows in any order wait on each other instead of deadlocking (tested with a reviews-only batch beside a batch carrying their pull request). Every writer of GitHub facts goes through this function. The nightly sweep (`apps/uw-app/github/sweep.ts`) is one of those writers: it writes each listing and each pull request it re-reads as its own batch through the same function, so it takes the same locks in the same `github_id` order and cannot deadlock a webhook batch. It records each run afterwards, in one statement on the repository row alone: `last_sweep` always, and `swept_through` only forward (`GREATEST`), so a retry overlapping a slow run neither regresses the watermark nor writes a fact twice.

Where there is no row to lock, a unique constraint is the guard: `delegations_supersedes_once` lets one renewal of a dead delegation insert and the command maps the other's violation to `stale_version`.

**Isolation is READ COMMITTED**, Postgres's default; nothing sets another level. The WIP count after the stage-claims lock and the stage re-read after the harness-stages lock rely on each statement seeing what committed before it began. Under REPEATABLE READ the snapshot is fixed at the transaction's first statement, so a count or re-read after a lock wait would miss the commit it waited for, and both the WIP limit and the lost-update guard would silently fail.

**One key space.** Every advisory lock is `pg_advisory_xact_lock(hashtextextended(key, 0))` over a string key, built by `advisoryLock(key)` in `packages/db/advisory-locks.ts` (the Drizzle store's `tx.lock` and the platform's grant commands and page re-parent use it; the event trigger writes the same expression in SQL). That file is the registry: the platform keys `acl-grant-commands` and `pages-reparenting`, and the prefixes `harness-stage-claims:`, `harness-stages:`, `harness_events:`, `github-issue:`, `persona-activation:`, `harness-run-persona:` and `zulip-topics:`, and the breaker's key `harness-breaker`. Its tests fail if one key is a prefix of another, if a kernel lock key's prefix is not registered, or if a numeric advisory lock appears anywhere in the repository. Two distinct strings can still hash alike (64 bits); the cost is two unrelated commands waiting on each other, never a missed lock.

## Events are the spine

Every kernel operation returns events; the kernel appends them and wakes the hub. Modules never call each other's internals; where one reacts to another, it reacts to an event. Item state is a fold; the play-by-play, the board, the dashboard feed and the audit trail are all reads over the same rows.

The vocabulary is a closed enum in `packages/contracts`, listed in PRD section 8.6. Adding an event is a contract change.

## The agent boundary

The MCP surface serves exactly the served verbs of the verb registry and nothing else. There is no verb for approving, merging, deploying, publishing or advancing past a human gate, on any host. A persona is configuration over the verb registry and the run-shape registry; a new verb, a new run shape or a new engine is reviewed code. The code is `apps/uw-app/mcp/`.

**Access.** `/mcp` is its own Access application with its own audience (`infra/access/uw-app.json`, `mcp`), and the rest of the host is the app application. The edge (`apps/uw-app/auth/principal-middleware.ts`) picks the expected audience by path: `/mcp` accepts only `ACCESS_MCP_AUD`, every other path only `ACCESS_AUD`, and a token for the other audience is `401 unauthenticated` (R34). Service tokens are admitted only by the `mcp` application, and the edge refuses a service-token identity on any other path `401`, so a credential an agent holds for `/mcp` never reaches `/api/*` as its owner. Both audiences are configuration (`infra/uw-app/wrangler.go-live.toml`), not secrets. A person can still hand an agent their browser session on purpose; that is outside what the edge can tell apart.

**The endpoint.** `POST /mcp` is behind its Access application (`apps/uw-app/mcp/routes.ts`, mounted in `app.tsx`). It is the SDK's web-standard Streamable HTTP transport, stateless (no session id) with JSON responses; `GET` and `DELETE` answer `405` with `Allow: POST`. A request carries one JSON-RPC message of at most 256 KiB; a batch is refused. One SDK `Server` is built per request and closed after it.

**Minting** (`apps/uw-app/mcp/mint.ts`). The edge turns an Access credential into an agent identity for the request. On `/mcp` a person's login is always minted as an agent, never `human:<id>`: it must send `x-uw-device` (`^[a-z0-9][a-z0-9-]{0,31}$`, `400 malformed_command` without it) and is minted `agent:<personId>/<device>`, interactive; a device the person's live service token is bound to is `403 not_permitted`, so a login and a runner never share an identity. A service token is looked up by its client id in `service_tokens`; with no live binding it is `401 unauthenticated`, and with one it is minted `agent:<personId>/<device>` for the bound person and device, not interactive. `x-uw-persona` and `x-uw-delegation` come together or not at all; with both, the identity is the delegated form `agent:<personId>/<device> as <persona> via delegation:<id>`. Minting does not check the delegation; the dispatcher does, on every call (below). Minting needs a live `editor` or `admin` grant at any scope (`403 not_permitted` otherwise), and the minted grants are exactly the owner's grants resolved for this request, so a revoked grant is gone on the next request. Each verb then checks the harness's area. A bare `agent:<persona>` is never minted at the edge: it is the beat principal of a delegation, which only the in-process host is given.

**Two hosts, one server.** `createVerbServer(context)` (`apps/uw-app/mcp/server.ts`) builds the server for a principal, an instant and a host. The `external` host is the HTTP route above. The `workflow` host is `connectInProcess` (`apps/uw-app/mcp/in-process.ts`), the same server over the SDK's in-memory transport. Only the run steps (`apps/uw-app/runs/steps.ts`) and tests import it (dependency-cruiser `in-process-host-only-in-run-steps`), and only the HTTP route, the in-process host and the test helpers build a verb server (`verb-server-only-in-the-hosts`); tests serve an arbitrary principal through `serveVerbsForTest` (`apps/uw-app/testing/in-process.ts`). The host forces the cost basis: `record_run_step` must say `subscription` from the external host and `metered` from the Workflow host, and anything else is `not_permitted` `{ why: 'cost_basis_is_the_hosts', expected }`.

**The Workflow host.** A hosted run is the `HarnessRun` Workflow (`apps/uw-app/runs/workflow.ts`, exported by the Worker entry; binding `HARNESS_RUN` in the go-live file only). Its core (`apps/uw-app/runs/run-core.ts`) runs read, scout, work and submit as named, checkpointed steps, each retried three times; a step opens its own connection at its own instant through `connectInProcess`, which takes a run id and the system principal (a run-host caller, S7-R43), never a principal: it asks `kernel.runs.scene` for the run's beat principal, which is refused unless the run is running, its delegation live, `write` held on the harness's area and the item held by the run under a live lease, and a refused scene opens nothing. Each connection is two servers for that principal: the model's, which lists and serves only the persona's toolset without `record_run_step` (the scout's only the read-only verbs within it) and re-checks the scene before every call (S7-R41, S7-R42), and the core's, which serves `resolve_context`, `record_run_step` (metered) and `submit_to_gate` to the run core alone. The model's loop also re-checks the scene after every turn and renews the lease every five minutes. The run kernel (`apps/uw-app/runs/deps.ts`, `runWiring`) is the only kernel given the GitHub read client for the review diff and the Reviewer review writes; the verb kernel is built with `hubWiring` and holds neither. A paused or breaker-hibernated run, and a run parked at a gate, wait in one-hour slices, each followed by a step that reads the run row, so a resume that lands before the wait is not lost, and a gate left undecided for 30 days stops the run `gate_wait_expired`. Every step, the host-only ones (hold premise, post review, close) included, waits this way when it is refused because the run hibernated, then runs again. Post review, when it runs again, first looks in the read model for a review by the run's Reviewer on the head, and records that review as posted, posting nothing (S7-R72). Only `apps/uw-app/runs/`, the in-process host and the sim call the run-host members, and only the minute cron calls the beat (`tools/architecture/runs-callers.test.ts`).

**The sandbox engines.** `claude-code-sandbox` and `codex-sandbox` run a CLI in a container instead of a tool loop in the Worker. The work step hands the engine the step's own verb server over HTTP (`OpenStep.http`, built in `connectInProcess` from the same context, toolset and per-call scene check as the model's client), never a principal. The engine opens one container session per step (`apps/uw-app/engines/sandbox/session.ts`), writes the MCP configuration and the prompt, runs the CLI with a placeholder key, and destroys the session in a `finally`, so the container keeps no state. Every outbound HTTP request from the container passes the egress proxy (`apps/uw-app/engines/sandbox/egress.ts`): `mcp.internal` goes to the step's verb server, the model host forwards only `POST` to its route's inference paths (`/v1/messages` and `/v1/messages/count_tokens` for `anthropic`, `/responses` for `openai`) and only the headers `content-type`, `accept`, `anthropic-version`, `anthropic-beta`, `openai-beta` and `user-agent`, so no container credential and no `cf-aig-*` control header reaches AI Gateway, before it sets the organization's key and gateway token (S7-R70). Every other host, path or method, GitHub included, is `403 egress refused` and logged by host and path. Before it forwards each model request the egress runs the step's `onTurn`, the same check the tool loop runs each turn: it re-reads the run scene and renews the lease every 5 minutes. When that check throws, the request and every later one answer `403 run halted`, and the engine rethrows the halt after the session ends, so a stop, a pause, a lapsed delegation or the breaker halts a sandbox step's model spend at its next request (S7-R69). The Durable Object classes (`apps/uw-app/engines/sandbox/classes.ts`, on `@cloudflare/containers`) start with the internet off and route all outbound HTTP through one handler to the egress the step bound for that session (S7-R46, S7-R47). The run core counts the tools called and the writes made over HTTP, and the engine records the sandbox's compute cost (wall time at `SANDBOX_MINOR_PER_HOUR`) beside the model cost. The containers, the classes' bindings and their migration are in the go-live file only.

**The tool list and the dispatcher.** `tools/list` is `toolsFor(principal, at)` (`apps/uw-app/mcp/tools.ts`): every registry verb served in v1 whose name holds no forbidden verb and, for a fixed-area verb, whose grant the principal holds, with input and output JSON Schema from the verb's own Zod schemas. `tools/call` is `callVerb` (`apps/uw-app/mcp/dispatch.ts`). A name that is not a served verb for this principal (a forbidden verb, an alias of one, an unserved verb, anything else) is the JSON-RPC error `-32602` with `Unknown tool: <name>`. For an identity that names a delegation, `callVerb` runs `kernel.delegations.beat` once per call before anything else, and its refusal (`delegation_not_found`, `not_permitted`, or `delegation_lapsed`, which records the lapse once) answers every verb, page and task verbs included (R35); the item verbs do not beat again. Arguments are parsed with the verb's input schema (`malformed_command` on failure). Every kernel read a verb makes is judged at the request instant (`{ at: context.at }`), the same instant the dispatcher's `can()` uses. Every handler is built by `gatedHandler` or `rowFilteredHandler` (`apps/uw-app/mcp/handler.ts`), and `createVerbServer` refuses at startup a handler no builder made, or a rows handler for a verb with a registry grant. A gated handler names the resource it touches, and the dispatcher runs the one central `can()` on it before the handler acts; when the caller may not read it, the reply is the handler's own not-found refusal, byte-identical to a missing id. A rows handler maps each row to its resource and the builder drops every row `can()` refuses. A refusal is an MCP result with `isError: true` and text `{"status":"error","reason":<closed set>,"detail":{…}}`; every call is logged with its outcome.

**The verbs.** Harness verbs (`poll_queue`, `claim_item`, `submit_to_gate`, `record_run_step`, `get_health`) call `kernel.reads` and the kernel's item commands. A delegated identity, a bare persona and a non-interactive device without a delegation see only what they may act on: the harnesses their live delegations with a capability other than `none` name, and nothing without one. Page verbs (`search_pages`, `read_page`, `write_page`) read through `apps/uw-app/pages/` and save through its `createPage` and `updatePage`; an agent's save of a `learning`, `skill` or `persona` page is only ever `suggested`, and it may not save a page any stage names as its instructions. Which page types are gated is one table (`apps/uw-app/pages/gating.ts`); the person page API never creates a gated page `active` nor moves one to `active` (`not_permitted` `{ why: 'activation_required' }`, R38), so a gated page reaches `active` only through its activation command. `resolve_context`, `query_entities` (`open_tasks`, `stage_items`) and `create_task` read pages and stages and write `tasks`. Persona activation's tool check (AB-8) is the kernel command `kernel.personas.activate`, which takes the page version the person read (`expectedVersion`) and answers `stale_version` when the stored page has moved on; with no software harness, or one with no stages, the failure is still recorded and the refusal says `why: 'software_harness_missing'`.

## The command API

People act on a harness through one route group, `POST /api/harness/:harness/commands/:name` (`apps/uw-app/commands/routes.ts`, mounted in `app.tsx` after the principal middleware). The route only builds the request from the context and answers; every person `/api` body is read through one bounded reader (`apps/uw-app/http/body.ts`, 256 KiB like `/mcp`), and a larger or unparseable body is `malformed_command`; the logic is `executeCommand` (`apps/uw-app/commands/dispatch.ts`), so tests can pass any principal. Every response body is exactly `{ "status": "accepted", "requestId" }` or `{ "status": "error", "requestId", "reason" }` with a closed-set reason; a refusal before the body is parsed carries no `requestId`.

**The order.** (1) The handler by name from the registry, else `not_wired`. (2) A database and a principal, else `database_not_configured` or `unauthenticated`. (3) The body parsed with `harnessCommandSchemas[name]`; a body whose `command` is not `:name` fails the literal and answers `malformed_command`, keeping a carried `requestId`. `:harness` is parsed with `z.uuid()`; a malformed id answers `harness_not_found`, byte-identical to a missing one (S6-R20). (4) The scope: for a `harness` command, `kernel.reads.harness` at the request instant, refused as `harness_not_found` (hidden equals missing); the area is the harness's. For `new_harness` (`activate_template`) the area is the body's `jdArea`. (5) The agent rule: a principal that is not a person is refused `not_permitted`, except on a handler marked `agents: 'recorded'`, which reaches the kernel so it records `gate_refused_to_agent`; `commandHandler` refuses that mark on any command but `approve`, `reject`, `take_over` and `override`. (6) `can(principal, handler.action, area)`, else `not_permitted`. (7) Every id the body names must belong to `:harness`: `itemId` and `beforeItemId` through `kernel.reads.item`, `delegationId` and `supersedes` through `kernel.reads.delegation`; one that is missing, hidden or in another harness answers `item_not_found` or `delegation_not_found`, byte-identical (S6-R19). A named `pageId` (enqueue, kickstart), and a stage's `instructionsPageId` in `create_stage`'s `stage` or `update_stage`'s `change`, must be a page the caller can read in the harness's area, through `readPage`; anything else is `page_not_found`, byte-identical to a missing page (S6-R56). The kernel checks a stage instructions page again before it writes: one that is missing, an `issue` page or outside the harness's area is `page_not_found`, so the foreign key and the issue-page trigger never answer for it. (8) The ledger, then the handler, then the settle.

**The request ledger** (`apps/uw-app/commands/requests.ts`, owner of `command_requests`, an exceptions row). Requests are keyed by (principal identity, `requestId`), so one person's `requestId` is never replayed to another. The ledger is read only after steps 4 to 7, so a caller whose grant was revoked gets the refusal, never the old outcome (S6-R18). A settled request with the same command and harness replays its outcome; one with another command or harness is `malformed_command`. A claim is an `INSERT … ON CONFLICT DO NOTHING`; a pending claim older than five minutes for the same command and harness is retaken; a claim that is still running answers `request_in_flight`. A handler that throws releases its claim, so a retry runs; release and settle both apply only to the claim with the request's trace id, so a run whose claim was retaken can neither free nor settle it. Each statement is autocommit on the request's connection, outside every kernel transaction. Every outcome is parsed with the strict outcome schema before it is stored (the table bounds it at 16 KiB). The cost of a crash between the kernel's commit and the settle is S6-D3. A run retaken while the first is still going cannot create a second item: the partial unique index `harness_events_one_item_per_request` admits one `item_created` per (actor, `requestId`), and when it fires the kernel's enqueue (and kickstart through it) finds the item the request already created (`harnessEvents.read.createdFor`) and answers `accepted`, so the retaken run settles `accepted` and every replay answers it (S6-R59, revised in the re-review). The nightly cron (`apps/uw-app/cron/request-retention.ts`, before the GitHub sweep) deletes requests settled more than 30 days ago, and claims more than 30 days old that never settled; a `requestId` reused after that runs again.

**Handlers** (`apps/uw-app/commands/handler.ts`). Every handler is built by `commandHandler` or `notWiredCommand` with a literal `action`, which brand it in a module `WeakSet`; `commandRegistryOf` refuses an unbranded handler, or a second handler for one command, when the registry is built (S6-R22). A handler's `run` parses the body again with its command's schema before the typed `run`. The command context carries the kernel, the caller (`{ actor, traceId, requestId }`, so every event a command appends carries the `requestId`), the harness and its stages, and four narrow capabilities the dispatcher builds (`apps/uw-app/commands/capabilities.ts`, S6-R57): `pages.read(pageId)` (the caller's page read at the request instant), `githubIssues.byNumber(repository, number)` (the read model), `importIssue(issue)` (the import path, which refuses an issue it may not import) and `gateKernel()`. It carries no database handle, no environment and no secret, and `tools/architecture/command-handlers.test.ts` fails any file under `commands/handlers/` or `commands/person/` that imports `@uw/db`, reads a `database` member (`.database`, a destructured `database`) or names the key `'database'` in any quotes (`c.get('database')`, `context['database']`). One file is exempt by name: `commands/person/gate-view.ts`, the gate view's GET route, which is not a command handler; it reads the database handle from the request context to open the ordinary kernel for `kernel.gates.view`. The gate GitHub opener comes from `PersonDeps` (`apps/uw-app/commands/person-deps.ts`), which `createApp(deps, person)` passes only to the harness routes (S6-R21). `gateKernel()` is the one place the human check is made: for a person principal whose identity is `human:<personId>` on a gate command (`approve`, `reject`, `take_over`, `override`, `recover_connectors`) it builds the gate kernel with that opener; for any other principal on a gate command it is the ordinary kernel; on any other command it throws. Only the capabilities module imports the gate kernel, and only the person deps import the gate GitHub opener (dependency-cruiser, with planted cases).

**The person surface** (`apps/uw-app/commands/person/`, ADR 0009). The handlers that touch gates, stages and delegation grants live here and nowhere else in `uw-app`. `gates.ts` serves `approve`, `reject`, `take_over` and `override` (`admin`, `agents: 'recorded'`) through `kernel.gates.decide`, and `recover_connectors` (`admin`, agents refused) through `kernel.gates.recoverConnectors`. `approve` and `override` pass the head the person saw (`head`) as `seenHead`; `override` carries its reason (a blank one is `malformed_command`); `reject` carries its findings. Each calls `context.gateKernel()`. For a person principal whose identity is `human:<personId>` that is the GitHub-wired kernel, so an approve or override at Ship refreshes the facts from GitHub, runs the ship rule and, after the decision commits, runs the merge connector; with no GitHub App configured the refresh answers `not_wired` and nothing is decided. For any other caller it is the dispatcher's ordinary kernel, which holds no GitHub client and records `gate_refused_to_agent` (S6-R27). An agent principal that cannot read the harness answers `harness_not_found` and records nothing.

**The checks** (`tools/architecture/command-routes.test.ts`). The registry serves exactly the contract's command names; every file under `commands/handlers/` and `commands/person/` that declares a handler uses a builder with a literal action; `dispatch.ts` calls `can()` before it runs a handler; no route is registered on an `app` or `routes` binding, and no `new Hono` is made, outside the reviewed route files (test files and `testing/` excluded, S6-R15); and every handler registered in `commands/routes.ts` reaches `executeCommand` or a kernel read (`kernel.reads.*`, `kernel.events.read`, `kernel.gates.view`) (S6-R23). Planted cases fail each.

## The live hub

PRD WB-3 and P23. `HarnessHub` (`apps/uw-app/live/harness-hub.ts`, exported from `apps/uw-app/index.ts`) is a SQLite-backed Durable Object on the WebSocket Hibernation API, one object per harness, named by `idFromName(harnessId)`. Its logic is `createHubCore` and `hubFetch` (`apps/uw-app/live/hub-core.ts`), which tests run on a fake state (`apps/uw-app/live/testing.ts`); the hibernation runtime itself has not run (S6-D18).

**What it carries.** A wake sends every open socket of that harness one message, `{"type":"wake","harnessId":…}`, parsed with the contract's `hubWakeSchema` before it is sent. It carries no event, item, page, position or identity. Wakes in one tick coalesce to one `setTimeout(…, 0)` flush. The object stores only `lastWakeAt`; `GET /stats` answers the connection count and that time. A socket that throws on send does not stop the others. `ping` is answered `pong` by the runtime without waking the object. The object closes a socket with 1000 and never echoes the client's code.

**Who reaches it.** A Durable Object has no public address: only code holding the `HARNESS_HUB` binding can call it, and `tools/architecture/hub-wiring.test.ts` allows the binding only in `apps/uw-app/env.ts` and the platform Hub adapter (`apps/uw-app/ports/hub.ts`). The object answers three internal paths, `GET /connect` (426 without `Upgrade: websocket`), `POST /wake` (a strict `{ harnessId }`, 400 otherwise) and `GET /stats`, and 404 for anything else. No route reaches the object yet. The live route (`GET /api/harness/:harness/live`) is to be the only caller that forwards a socket to `/connect`, after it reads the harness through `can()`, so a client cannot subscribe to a harness it cannot read. A wake only tells a client to re-read, and every read goes through the access-checked read routes.

**Who wakes it.** The kernel wakes the hub after each committed transaction that appended events, once per harness, and drops a failed wake (S6-D17). The adapter bounds each wake at 2 seconds; a wake that times out (`hub_wake_timed_out`) or that the hub refuses (`hub_wake_refused`) is logged and never fails the command. The command, MCP, queue and cron kernels build their hub with `hubOf(env, logger)`, which falls back to the not-wired hub while the binding is absent. The queue and cron kernels wake each harness once at the end of their unit of work (`apps/uw-app/unit-hub.ts`). The sweep counts the wakes it owes inside its 900-subrequest bound (S6-R54): every GitHub call and every repository start leaves room for the wakes already owed plus one for the repository in hand (a repository names at most one harness), so when the bound cannot cover them the sweep defers the remaining repositories, as it does when GitHub calls run out, and never skips a wake for a change it stored.

**Where it is declared.** The binding and its `v1` migration (`new_sqlite_classes = ["HarnessHub"]`) are in `infra/uw-app/wrangler.go-live.toml` only, for staging, production and preview (S6-R38): a Durable Object migration cannot be undone by a redeploy, so it waits for the go-live switch-on. Until then the live client polls.

## Reaching a person

PRD NT-1 to NT-4, P24, P25. Decisions S9-D1 to S9-D16.

**After commit.** The kernel's store is wrapped so that after a transaction that appended events commits, the kernel plans one wake per triggering event (`packages/harness/notify/`): a parked `submitted_to_gate` is `gate_waiting`, and `delegation_lapsed`, `run_failed` and `stage_advanced` are their own reasons. Planning reads the item, its holder before the transaction and the grant holders of the area, outside any transaction. Nothing in it decides a gate or writes a gate decision. The wakes are sent strongest first, after commit, and awaited inside the command, MCP call, queue batch or cron run that caused them (S9-D12). A failure after commit is swallowed; the command's outcome never changes.

**Recipients.** A gate wake goes to every active person whose grants give `admin` on the harness's area and cover every domain of the item (what they could decide now). A lapse goes to the delegation's person while they hold `admin` on the area, else to every other area admin. A run failure goes to the person behind the item's holder, else the run's delegation's person, else the device owner. A stage advance goes to the person behind the holder (or, for a parked item, behind the submit that parked it). A person is never woken for their own `human:` action. The minute cron records the lapse of every expired delegation that has none, so an expiry wakes its person within a minute (S9-D16).

**Presence.** The hub tags each person socket with the screen and item its view connected for; a recipient on that screen (`gates` for a gate, `item` for the item, `home` for a lapse) is present, and present means suppressed. A presence read that fails or takes more than 2 seconds is "not present".

**Push.** `apps/uw-app/notify/push/` owns `push_subscriptions` and `push_cooldowns`. A person subscribes and unsubscribes their own devices at `/api/push/*` (agents are refused). For each recipient: present is `suppressed`; no VAPID configuration is `not_configured`; no device is `no_device`; otherwise one SQL statement claims the person's cooldown window (10 minutes; a stronger rank opens a new one), and only the claimant sends, so two wakes on two connections send once. Every device gets the strict payload `{ harness, reason, link }`; a 404 or 410 prunes the device. Each decision is one log line with the wake's trace id, never an endpoint or a key.

**Zulip out.** Gate, lapse and run-failure wakes post once, regardless of the cooldown, to the item's topic (`<harness key>/<item ref>`, or the harness key for a harness-level lapse) in the channel `ZULIP_CHANNELS` maps the area to. The post is the harness key, the item ref, one fixed sentence and the absolute link, nothing else. The first successful post links the topic on the item with a `zulip_topic_linked` event.

**Zulip in.** The bot's outgoing webhook reaches `uw-ingest` at `/webhooks/zulip`. The token is compared in constant time (SHA-256 of both sides) and stripped before the queue. The queue handler ignores private messages, finds the item by topic, requires the message's channel to be the harness's area channel, maps the sender's email to an active person (or none) and records one `comment_recorded` as `agent:ingest`. It decides nothing and acts as no one.

**The installed app.** Home carries the notifications control (`apps/uw-app/islands/browser/push-subscribe.ts`). The service worker shows a push with the reason's title, names the harness in the body, tags it with its link so a second wake for the same gate replaces the first, and opens the link on a click.

## The design tokens

PRD WB-11 and ADR 0007. The five brand colours are `--uw-brand-*` in `packages/ui/tokens/brand.css` with the brand guide's values. `theme.css` maps them to semantic tokens for light, system dark and forced dark (`data-theme`); `type.css` and `layout.css` hold the type scale, spacing, radii, breakpoints and sidebar width. `packages/ui/app.css` resets Tailwind's default colours, fonts, sizes, radii, shadows and breakpoints and declares a theme whose every value is one of these tokens, scanning only `packages/ui/components/**/*.tsx` and `apps/uw-app/**/*.tsx`, not their `*.test.tsx` and not `dist/`; Tailwind already skips `node_modules` and gitignored paths. `pnpm ui:css` (`tools/ui/build-css.ts`, through Tailwind's programmatic API, `@tailwindcss/node` with `@tailwindcss/oxide`'s scanner, so no file watcher is installed) builds it and commits the result as `packages/ui/generated/app-css.ts` with a hashed path (S6-D23).

**Contrast.** Inspire on white is 2.56:1, so Inspire is never a text colour on a light surface: links are Ocean in light and Inspire in dark, and text on Inspire, Cultivate or Kindle is `--uw-on-accent` (S6-D21). The focus ring is `#0095ca` in light (Inspire's hue, darker), not Ocean: the sidebar is the Ocean panel, and the ring must reach 3:1 against the panel, the page and the surface in both themes (S6-R47); Ocean on the panel is 1:1. `packages/ui/tokens/contrast.test.ts` holds every text pair to 4.5:1 and the focus ring and Kindle to 3:1, in both themes.

**What `packages/ui` holds.** The tokens, the theme and the built stylesheet, and the pieces under `packages/ui/components/`: the shell (shell, sidebar, top bar, page head, segmented control, theme switch), the content pieces (card, badge, chip, table, KPI, note, evidence label) and the harness pieces (human action, gate callout, lane, kanban card). Each piece takes plain strings and escapes them; none renders HTML it was handed. Ids that link a heading or a reason to its control come from a key the caller knows is unique (the stage key, the item id), encoded one-to-one, never from a title. `tools/ui/shell-once.test.ts` fails when a piece is defined a second time outside its owner file, and when any element other than `HumanActionButton` carries a literal `name` or `value` of `approve`, `reject`, `take_over` or `override`. The human action (`human-action.tsx`) is the one place a gate decision is offered: a submit button (a refused one stays focusable, `aria-disabled`, and does not submit), plus the small mark the Flow view puts on Ship. Kindle marks a human action and nothing else, so `tools/ui/kindle.test.ts` fails when a Kindle class (`-kindle` or `kindle-soft`) or a bare `kindle` string appears in any component or app source, or app stylesheet, other than `human-action.tsx`. Kindle is a fill or an edge, never a text colour: on a light surface it is below 4.5:1, so text on it is `--uw-on-accent`, and the gate mark is ink on the soft Kindle fill. The gate callout's facts show the parsed declaration, the recorded tier and domains with the head they were derived at, optionally the tier the rule derives now and the resolved review providers, and the head you approve, never the pull request body or GitHub's rendering of it. That head is one value: the facts render it and the hidden `head` input the approve sends. Showing a decision only to people is presentation: `/api` refuses agents, and the kernel refuses an agent's decision.

**Checks.** `tools/ui/tokens-agree.test.ts` (every theme value is a token; every semantic colour has a theme colour), `tools/ui/no-hex.test.ts` (no hex colour in any string or template literal, read with the TypeScript scanner, and no colour function, in `apps/` or `packages/` outside the token files and the generated stylesheet; a digits-only hex such as `#123` reads as an issue reference, so it is flagged only where styles are written: `.tsx`, `.css`, `.html`, `packages/ui/` and `apps/uw-app/islands/`), `tools/ui/generated-css.test.ts` (the committed stylesheet is the current build and names no colour outside the theme) and `packages/ui/tokens/tokens.test.ts` (brand values; light and dark define the same tokens).

**The screens.** Every screen is a Hono route in `apps/uw-app/views/routes.tsx` whose handler sits in `apps/uw-app/views/screens/` and is listed in `views/registry.ts`; the pieces they share (the frame, the paths, the gate panel, the Flow diagram, the play-by-play rows) sit in `views/parts/`. A screen reads only through `kernel.views.*`, `kernel.reads.*` and `kernel.events.read`, with the request's principal at the request's instant, so what it shows is what that person may read, and a harness or item they may not read renders the same not-found page as one that does not exist. `renderScreen` wraps the body in `Shell`. The islands bundle (`apps/uw-app/islands/browser/`, built by esbuild into `apps/uw-app/generated/islands.ts` and served at `/assets/islands-<hash>.js`) wires every `CommandForm` to the command API and keeps a page live: one live session per harness on the page, and on a wake one GET of the same URL with `x-uw-fragment: main`, whose answer is the inner HTML of `<main>`, morphed in place; a form the person has edited is never replaced, and an older answer never replaces a newer one. The Gates view, a gate and Home also refresh every 60 seconds, because GitHub facts change without an event. Every response carries a Content-Security-Policy that allows only same-origin scripts and the hashes of the two inline theme scripts. `/health` and `/health/:indicator` sit behind Access and need a principal; `/health/probe` stays public for the deploy probe and answers only the four platform indicators.

## GitHub facts

GitHub is the source of every fact the Ship gate reads (PRD GH-1 to GH-7). Nothing here has run against GitHub yet: every test uses fixture payloads trimmed from GitHub's documentation, a fixture `fetch` (`fixtureGitHub()`) and a key pair generated in the test (PRD DX-8).

**The App and its secrets.** The GitHub App is declared in `infra/github/app-manifest.json` with `metadata: read`, `issues: write`, `pull_requests: read`, `checks: read` and `contents: write` (the merge and the tag), and the events `issues`, `pull_request`, `pull_request_review`, `check_run` and `push`. `uw-app` reads three Worker secrets, `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID` and `GITHUB_APP_PRIVATE_KEY` (PKCS#8); with any one absent GitHub is not configured, and each caller answers `not_wired` or logs and does nothing. `uw-ingest` holds `GITHUB_WEBHOOK_SECRET` for the signature check.

**The client** (`apps/uw-app/github/`). `session.ts` signs the App JWT with `jose` and mints one installation token per unit of work (a delivery, a sweep run, a connector run), scoped to that unit's one repository and to its client's permissions (S5-R42), and checks the token's expiry. No function returns a token or the JWT, and no log line carries either. Three clients open a session: the read client (`client.ts`), the comment writer (`comments.ts`, the cross-reference comment only) and the ship writes (`ship-writes.ts`, the merge and the tag, imported only by `merge.ts`). `fetch` is bound at the composition root. dependency-cruiser enforces who may import what: the read client only under `apps/uw-app/github/` and the queue root (`apps/uw-app/queue/worker.ts`), and `app-config.ts` there and in the cron sweep root (`apps/uw-app/cron/github-sweep.ts`); the session only in the three clients; the token module and every `@octokit` package but the webhook signature check only in the session; the ship writes only in `merge.ts`; `merge.ts` only in `apps/uw-app/ports/connectors.ts`; anything under `apps/uw-app/github/` only from the module itself, `apps/uw-app/ports/`, the queue root, the cron sweep root, the app test helpers and tests (so no route reaches `deps.ts` or `sweep.ts`); nothing under `apps/uw-app/mcp/` or `apps/uw-app/engines/` imports `apps/uw-app/github/`.

**The read model** (`apps/uw-app/github/facts/`). Six tables, `gh_repos`, `gh_milestones`, `gh_issues`, `gh_prs`, `gh_check_runs`, `gh_reviews`, keyed on the GitHub id and written only here. `normalise.ts` turns a webhook payload or a REST answer into a fact batch (an unknown check status or conclusion maps to a value that never reads green; a value without a full SHA is dropped or makes the delivery malformed). `upsert.ts` has the one guarded upsert, `upsertFacts(db, batch, freshAt)`: a row changes only for a value that differs and, on issues and milestones, a GitHub `updated_at` that is not older, and on pull requests a newer `updated_at` or an equal one at the same head (GitHub's `updated_at` has one-second resolution, so an equal one at another head only refreshes freshness and never moves the head back); a completed check never goes back; a dismissed review stays dismissed; a change of head SHA, base SHA or base ref clears the stored file list. Changed files are fetched by `${base.sha}...${head.sha}` with full SHAs and stored against that head and base (`recordFiles`). Two entry points call it: the queue consumer's GitHub handler (`apps/uw-app/github/ingest.ts`, then `follow-up.ts` for the files and the issue import) and the nightly sweep. `queries.ts` holds the facts query, `pullRequestFacts`, which the platform adapter answers from.

**The platform GitHubFacts adapter** (`apps/uw-app/ports/github-facts.ts`). `pullRequest` reads the read model and never calls GitHub. `refresh` re-reads the pull request (head and base), its reviews and the check runs on its head from GitHub, writes them through `upsertFacts`, reads the files again for a new head or base, and answers the read model; with no GitHub client it answers `not_wired`. Only the gate commands' kernel (`apps/uw-app/commands/person/gate-kernel.ts`) is given a read client and the ship writes.

**The sweep** (`apps/uw-app/github/sweep.ts`, `apps/uw-app/cron/`). A nightly cron (`17 3 * * *`, declared in `infra/uw-app/wrangler.go-live.toml` only) sweeps every repository the App is installed on, least recently attempted first and then oldest `swept_through`. Per repository it lists issues and pull requests by keyset from the watermark less 10 minutes (`since`, deduplicated by id), re-reads every open pull request's checks, reviews and files, retries pending cross-reference comments and imports, each batch through `upsertFacts`. The watermark (`gh_repos.swept_through`) moves only forward and only to the newest `updated_at` whose items are all stored; every run records `last_sweep` with its outcome (`ok`, `deferred`, `capped`, `failed` or `stalled`), the point it held at and why. A run stops before 900 subrequests (`maxSubrequests`) and 30 listing pages.

**The assembler** (`packages/harness/gates/ship-input.ts`) is the ship rule's only caller, through `approve-at-ship.ts`. An approve or override at Ship refreshes the facts before its transaction; facts stamped more than 60 seconds either side of the decision are `facts_stale`. The pull request counts only when its repository and head repository are the harness's, its number is the item's, its head ref is `harness/<item>`, its base ref is the repository's default branch (`gh_repos.default_branch`, read again by the refresh, so a renamed default branch is picked up; S5-R49) and its head is a full SHA. A harness therefore cannot ship into a release branch in v1. On that head, a check counts only from the `github-actions` app, named for a CI job, the latest run of that name deciding; a review counts only from a Reviewer identity (`packages/harness/github/reviewers.ts`, by login), the reviewer's latest decisive review deciding, and only an `approved` one counts.

Green CI is not a guard on its own. Code in a pull request runs in CI, and a workflow token with `checks: write` could create a later check run named for a CI job that concludes `success` on the head, which the latest-run rule would take. Every workflow sets its token permissions without `checks: write` (`tools/ci/workflow-permissions.test.ts`), and a pull request that edits `.github/` to grant it is high tier (`.github/` is protected under `infra`). The guards are the Reviewer approval on the head and the person who approves; the checks are evidence they read.

**Risk from the files at the head.** The tier at Ship is re-derived from the changed files compared at the PR's current head and base (each path and each rename's previous name), the item's ratcheted tier and domains carried forward, and the parsed declaration (`packages/harness/github/declaration.ts`), which opens the PR body and can only raise the tier. Files at another head or base, no files or no declaration is `riskTier: null` and the rule refuses `risk_tier_undeclared`. The derivation is recorded as `risk_derived` with its head, and with the repository and base it was compared against (contract 9.1.0). `submit_to_gate` derives from the same facts, never from the agent's input.

**The branch convention.** An item's work lands on `harness/<itemId>`; a claim names that branch and the commit to start from. A claim of an item whose branch was abandoned (its lease expired with a head recorded, `branch_abandoned`) starts from the item's expected head unless the claim sets `adoptBranch`, which reads the tip of the item's pull request from the read model before the transaction and records `branch_adopted`. The claim path is reachable by agents and holds no GitHub client, so adoption never refreshes: it takes only facts whose `freshAt` is later than the abandonment, the `at` of the item's last `branch_abandoned`, or the lease's expiry when this claim records the lapse itself (S5-R50); older facts are `facts_stale`, and a webhook for the pull request after the abandonment makes a later claim adoptable, however much later; the adopted tip becomes the item's expected head. `adoptBranch` with no abandoned branch is `malformed_command` (`no_abandoned_branch`), and a branch that cannot be adopted (no open pull request from `harness/<item>` in the harness's repository, a fork's head, or a pull request in another repository) is `not_permitted` (`branch_not_adoptable`).

**Issue import and the cross-reference comment** (`apps/uw-app/github/import.ts`). An open issue carrying the `harness` label, in a repository a harness names, becomes one item: the import writes the issue page (`apps/uw-app/pages/issue-pages.ts`, type `issue`, slug `issue-<githubId>`, written only by the import's identity), then `kernel.items.importIssue` (idempotent on the issue's GitHub id), then the cross-reference comment. The comment is claimed on `gh_issues`, looked for among the App's own comments on the issue, and posted only if absent. A person's `import` command (`apps/uw-app/commands/handlers/import.ts`) runs the same import with no GitHub client, after checking that the body's repository is the harness's (S6-R31): it logs `cross_reference_deferred` and leaves the comment to the nightly sweep (S6-D16). A removed label is recorded once per item by `kernel.items.labelRemoved` and deletes nothing. The import trusts the `harness` label whoever applied it, so `harness` must never be a label an issue template applies (`labels:` in `.github/ISSUE_TEMPLATE/`): a template would let any outside author create items whose titles reach agents. `.github/` is protected under `infra`, so adding such a template is high tier.

**The merge connector and `outcomeOf`** (`apps/uw-app/github/merge.ts`). The merge re-reads the live pull request with a one-repository ship token and refuses before any write another repository's pull request, a head in a fork or on a branch other than `harness/<item>`, a head other than the decided one, a base ref other than the repository's live default branch (`base_not_default_branch`, read from the pull request's base repository) and a base other than the decided one. It squash-merges with GitHub's `sha` guard, tags the merge `harness/<item>`, and answers a pull request already merged at that head, into the default branch and the decided base ref, without merging again; a pull request a person merged into another base is never answered as a success. `outcomeOf` reads the same pull request and the tag and writes nothing: it answers the merge that happened, `null` only when GitHub says nothing was merged at the expected head, and a refusal when GitHub cannot be read.

**The recovery sweep** (`packages/harness/gates/recover.ts`). `kernel.gates.recoverConnectors(caller, { harnessId })`, a person with `admin` on the harness's area, finds every approval that has waited more than 15 minutes for a connector outcome, asks `outcomeOf` with the repository and base recorded in the approval's own transaction (its `risk_derived`), and records `connector_succeeded` (and the stage exit, if the item is still parked on that approval), or `connector_refused` with `connector_lost` only when `outcomeOf` answers `null`. Any refusal from `outcomeOf` refuses and records nothing: an unwired connector is `not_wired`, and anything else (GitHub unreadable, another repository, a head elsewhere, a malformed request) is `facts_stale` with the connector's reason. No timer runs it; a person does, through a command route that step 6 adds.

## The sim

`sim/` is the kernel on test adapters. `createWorld()` gives a scenario one clone of an embedded Postgres migrated once per process, the ten test adapters, one settable clock starting `2026-10-01T09:00:00.000Z`, and `createKernel` over them; `createSimHarness(template, fixture)` builds a harness from a template. Scenarios in `sim/scenarios/` are named for the PRD requirement they prove: `KN-10.activation-refuses-a-bypass.ts`, `KN-13.agent-cannot-write-decision.ts`, `KN-16.delegation-lapses-when-grant-revoked.ts`, `DX-7.software-template-end-to-end.ts`. Assertions are on the event log and the folded item state.

The cockpit (PRD DX-4, DX-5):

```
pnpm sim -- <scenario>      run one scenario; print the event log and the folded state
pnpm sim -- all             every scenario
pnpm walk -- <template>     every path from Package to an external effect, and the gate each crosses
pnpm trace                  PRD requirement IDs with neither a scenario nor a test
pnpm trace:built            the same list; fails only on requirements whose step is marked Built
pnpm check                  lint, format, typecheck
pnpm verify                 the whole chain, the same one CI runs, including walk:all, trace:built and sim:all
```

A deployed Worker is touched for three things: platform adapters, rendering, and the tests only real infrastructure can prove. Everything else is proven in the sim first.
