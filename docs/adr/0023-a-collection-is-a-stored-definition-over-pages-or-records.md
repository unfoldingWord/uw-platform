# A collection is a stored definition over pages or records

The Notion databases the platform replaces (Program Portfolio, Projects Kanban, Colleague Directory, task lists) are database-shaped pages: typed properties, relations, saved views. Building each as its own screen would make every new one a pull request. `prd/Databases and Views - Design Proposal.md` Part 5 proposed decisions A to D and F; C was ruled by an owner on 2026-11-21. This ADR records them as built in #206.

**A. A collection's schema is data.** A **collection** is a row of `collections` with one row of `collection_properties` per property. Each property's type-specific settings (options, status groups, relation target, rollup, computed inputs, read-through feed) are a JSON value validated by the property catalogue's Zod schemas in `packages/contracts/collections.ts`. On every write the whole definition is compiled to a Zod schema at runtime (`compileRowSchema`) and every row written through a collection command is parsed by it. Each change to the definition advances `collections.version` and appends the full definition to `collection_versions`. The built-in collections (tasks, directory, portfolio, program, project, OKR) are TypeScript values validated by the same schema and inserted by the same create path, so there is one mechanism. Changing a definition is a person's command on the collection's area with `admin`; no verb does it. A **locked** collection refuses every definition change except unlocking.

A property's type change is all or nothing: every row is converted in one transaction, and if any row would not fit, nothing is written and the refusal lists the rows. The definition's version advances only when every row fits. Properties live in their own rows, rather than inside one JSON blob, so a saved view's rows can hold a foreign key to a property and a deleted property removes them.

**B. Values live in `pages.frontmatter`; relations in `page_links`.** A page collection's property values are keys of the page's frontmatter: no entity-attribute-value table and no runtime DDL; Drizzle stays the only schema. A page row belongs to its collection through `pages.collection_id`. Its frontmatter is written only through a collection command, which calls the pages module's narrow writers (`createCollectionPage`, `setCollectionFrontmatter`), so `pages` keeps one writer (rule 3). `update_page` keeps a collection page's frontmatter as stored, so the page editor still saves its body. A relation is a `page_links` row whose `rel` is `<collection key>.<property key>`; a two-way relation's other end reads the same row backwards. Body links rebuild only their own `rel` values, so a save never drops a relation. Frontmatter values are read in SQL by typed extractor functions (migration `0065`); dates are `YYYY-MM-DD` built with `make_date`, which is immutable and depends on no time zone, so it can back an expression index.

**C. A collection owns no money.** The property catalogue has no money type and a `number` property has no currency or money format. Money is a **read-through** property from a closed set of feeds (`budget`, `actuals`, `committed`, `remaining_need`, `balance`, `income_by_source`, `sage_program_id`) served by the budget module's views. No collection command writes one; `set_property` on a read-through property is refused with `property_not_writable`. Programs are the budget plan's cascade nodes, the `program` pages themselves, and carry their Sage Intacct program ID through `sage_dimension_map`. Until #178 builds the dimension map and #179 to #181 the figures, every feed answers `not_wired` and a project's money shows "no budget lines yet".

**D. Computed properties are a closed set.** `sum`, `difference`, `count` and `date_until`, and rollups over a relation with `count`, `sum`, `show_unique` and `percent_complete`. No formula language; if one is ever wanted, an existing sandboxed expression library is used (AGENTS.md §5).

**F. A collection lists pages or typed records.** `collections.row_source` is `pages`, `tasks` or `people`. Each property declares its source: a frontmatter key, a typed column of the record table, a relation, a computed value, a read-through feed, or a system field (created and last-edited time and by, and the time the row entered its status's complete group). The query engine compiles each source to its own SQL; views do not know the difference. A write to a record goes through its owner module's command: `tasks` through the tasks module, `people` and `directory_entries` through the people module.

**Rejected.**
- **Zod in code only.** Every new collection would need a deploy.
- **A real column per property (Twenty, NocoDB, Baserow).** Runtime DDL from a Worker through Hyperdrive breaks "Drizzle is the only schema". Data queried hard already lives in typed records.
- **One JSON blob per view or per definition.** A deleted property would leave dead filters behind, as three Notion views have today.
- **A stored money type behind a permission.** It would be a second writer of figures the budget module owns.

**Consequences.** Every page type that holds collection rows (`entry`, `portfolio`, `program`, `project`, `okr`) has a permissive registry schema; its real schema is the collection's compiled one, and `create_page` refuses those types so a row is always created through its collection. A collection with very many rows may outgrow JSONB extraction; the answer then is a typed table under decision F, not runtime DDL. The spike numbers are in the #206 pull request.
